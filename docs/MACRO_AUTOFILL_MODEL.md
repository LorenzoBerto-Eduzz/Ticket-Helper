# Macro Autofill Model

`Colocar produtor em cópia` uses the selected invoice support email. It opens Cc in the focused ticket composer, enters the email, and presses Enter. HubSpot may display a contact name rather than the address inside its recipient tag, so success means the committed Cc tag count increased after Enter. Only then does TicketHelper remove the macro label. A standalone label removes its paragraph and one empty paragraph below, its following `<br>` and one extra `<br>` below, or the corresponding two newline characters; an inline label removes only itself. The blank line above remains. Missing selection, unavailable Cc control, changed ticket ownership, or an unconfirmed new Cc tag leaves the label intact. `Colar nome do produto` inserts only the selected product name, formatted like the copy action.

`Colar ID da fatura` inserts the numeric invoice ID selected for the focused ticket; it does not require the BO popup to be open. `Colar nome do cliente` uses the part before `@` when the ticket name itself is an email, capitalizing only its first letter (for example `user.name@example.invalid` becomes `User.name`). The name copy shortcut and popup row use the same rule.

TicketHelper's HubSpot-only macro autofill is configured in Options under **Autopreenchimento de Macros**, below Shortcuts and above Producer Notices. The user stores exact, case-sensitive label text with an action choice in `chrome.storage.local` under `macroAutofillRules`. An empty label deletes its row; an unassigned action leaves a saved label inert. Duplicate labels are rejected in Options. Available actions are `Colar email de suporte` (selected Fatura), `Colar nome do produto` (selected Fatura), `Colar ID da fatura` (selected Fatura), `Colocar produtor em cópia` (selected Fatura), `Colar dados da fatura` (the selected invoice summary), `Colar nome do cliente` (first word of the active ticket name, capitalized), and `Saudação por horário` (device local time: Bom dia 04:00–11:59, Boa tarde 12:00–18:59, Boa noite 19:00–03:59). Further actions should be added to the shared action registry and resolved through focused handlers.

Options rows use one shared divider at about 38% of the available width. Each label field is right-aligned against it and grows leftward; if needed, the divider moves right for every row together. The action field starts at the shared divider. The `+ Adicionar Etiqueta` button sits closer to the heading when the list is empty. Both it and `+ Adicionar Aviso` use a fixed one-fifth section width.

ProKeys 4.0.2 inserts a completed rich-text macro as a new `.prokeys-snippet-text` element and fires an input event on that span. `macro_autofill.js` captures that event before HubSpot normalizes the editor, and also observes newly added nodes and their descendants. It inspects only ProKeys snippets, not typing or ordinary paste. Each insertion is processed once. If HubSpot removes the wrapper before the selected-invoice value returns, replacement is allowed only when the exact inserted text still exists at the captured position. A live HubSpot check must confirm the editor retains the replacement. If a future ProKeys version stops exposing the marker, adapt the trigger rather than scanning every keystroke.

Before any replacement, the content script requires the focused HubSpot editor, ticket route, visible ticket header, locally active ticket, and popup owner tab/epoch to agree. It repeats those synchronous checks immediately before changing the text, so a route or focus switch while a value is pending leaves the label untouched. The owner epoch is sent with each ticket-data request; A-B-A switching cannot reuse an answer from A's earlier ownership. A greeting uses the same focused-editor gate even though its value comes from local time. The checks use the already available page and owner state and add no polling or extra network request.

The first resolver asks the background for the current ticket's selected Fatura support email using the existing `GET_SELECTED_FATURA_SUPPORT_EMAIL` result guard. It does not copy to the clipboard, focus a BO tab, or start a BO search. The background checks the sender tab, ticket ID, ownership epoch, selected invoice ID and product-row index, BO tab origin, and still-current selection before returning a lowercase email. The BO content script requires the exact visibly selected row, matching invoice ID and buyer signature; a different product within the same invoice cannot supply the value. An explicitly pinned invoice remains valid for its owning ticket even if it is outside the ticket's normal account search results. An unavailable or uncertain value leaves the label unchanged. The content script also rechecks snippet text and active rule revision before replacing exact occurrences inside that newly inserted snippet and dispatches one input event for the editor.

When a label starts immediately after a `<br>` or another element boundary, the replacement range must start in the label's own text node; its end must stay in that same node when the label ends at a boundary. Otherwise deleting the range can remove the surrounding line break and join separate macro lines. Keep the original macro structure and formatting around each label.

`Colar dados da fatura` uses the same five-field summary as the selected invoice copy command. It captures BackOffice's native invoice data without writing raw customer details to the clipboard, checks the selected invoice and product row, and returns only Fatura, Valor, Valor pago, Conteúdo, and Data da compra. For an Order Bump, Conteúdo lists the selected product first, followed by other contiguous same-ID products in visible top-to-bottom order, with commas and line breaks between names. Full product names come from their accessible labels when the visible text is truncated. Missing fields, changed selection, or changed product rows leave the macro label unchanged. The rich-text replacement inserts `<br>` elements for newline characters, including the blank lines between fields.

The owner observed support-email replacement working in an actual ProKeys expansion. The first implementation joined a separate tag line to the preceding line; boundary-aware replacement now preserves the line break. Continue live checks for the other actions, surrounding rich formatting and caret, ordinary typing/paste exclusion, and stale-invoice refusal after ticket switching. Automated tests cover label matching, line-break boundaries, and ownership guards but cannot certify every third-party editor behavior.
