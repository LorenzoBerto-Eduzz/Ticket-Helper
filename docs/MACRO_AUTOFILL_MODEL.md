# Macro Autofill Model

The initial final MacroAction trigger requires a focused reply editor with a ready ticket context. After opening HubSpot's send/status modal, guard each step by the same visible ticket route and owner epoch; the modal can move focus away from the editor and temporarily obscure the ticket header used to calculate context readiness. A different route, owner epoch, or hidden tab stops preparation.

For a final MacroAction dependent dropdown, open the field-owned portal named by `aria-owns`, enter the full display label in its Search input, wait for the exact `.Select-option [data-option-value]` to be focused, send Enter to that input, and confirm through the current field button. This applies to solution type, validation, and pending type. The initial send-options menu remains a direct button choice; the plain text and date fields remain direct entries. A missing focused match or unconfirmed selection leaves the final label pending. The service worker logs any failure code received from the HubSpot page in addition to showing the red notice.

The focused-option wait observes the typeahead's `class` and `aria-activedescendant` changes, so it can continue as soon as HubSpot focuses the exact result. The wait timeouts are failure bounds, not delays on a successful path. Only `Solucionar como resolvido` has been confirmed in live HubSpot so far; all eight mappings have automated coverage.

When a final MacroAction selects a dependent dropdown option, confirm it using the current field button rather than the button that opened the menu. HubSpot may replace that button during a React update. Failure diagnostics are emitted in the HubSpot page Console and a red notice, not in the extension service-worker Console.

Composer preparation is specific to HubSpot's **Email** channel, identified by the channel control's `Email` icon. A **Chat Eduzz** composer has a different Settings option (`Press 'Enter' to send`) and must not have its menu opened or checkbox changed by TicketHelper. Preparation runs when the composer/editor appears or changes, with one attempt per loaded composer, ticket, editor, and channel once its Settings button exists; ordinary typing does not invoke it. If the email checkbox does not appear, later keystrokes and editor mutations do not reopen Settings. If the channel changes while the email settings menu is opening, stop before changing a checkbox.

`Colocar produtor em cópia` uses the selected invoice support email. As soon as the HubSpot reply composer loads, TicketHelper opens its Settings menu if needed and checks **Always show email details**; it leaves an already checked option untouched. For the MacroAction, it uses the visible Cc field or opens the Cc button in the focused ticket composer, enters the support email, presses Enter, waits 150 ms, and restores focus to the reply editor. It does not compare recipient chips: an address already in Cc is also a completed flow. The macro label is removed only after this sequence completes for the same ticket; failure to reach Cc leaves it pending. A standalone label removes its paragraph and one empty paragraph below, its following `<br>` and one extra `<br>` below, or the corresponding two newline characters; an inline label removes only itself. The blank line above remains. Missing invoice selection or changed ticket ownership leaves the label intact. `Colar nome do produto` inserts only the selected product name, formatted like the copy action.

`Colar ID da fatura` inserts the numeric invoice ID selected for the focused ticket; it does not require the BO popup to be open. `Colar nome do cliente` uses the part before `@` when the ticket name itself is an email, capitalizing only its first letter (for example `user.name@example.invalid` becomes `User.name`). The name copy shortcut and popup row use the same rule. `Colar email do cliente` inserts the active ticket's email in lowercase; it needs no selected invoice and leaves the label intact when the email is missing or the ticket ownership changes.

`Baixar comprovante do reembolso` requires the focused ticket's selected Fatura and exact selected product row. It reuses the BO menu action that clicks the enabled refund-receipt button. After that click succeeds, it clicks the focused HubSpot reply composer's **Attach file** button and the visible **Upload new file** option. The upload option opens the browser's file selection flow; TicketHelper does not select a file or verify that the download or attachment finished. Only after both clicks does it remove the macro label, using the same standalone-line removal as `Colocar produtor em cópia`. A missing BO option, changed ticket/Fatura, or missing composer control leaves the label pending. Run this side effect after other MacroActions in the same inserted text so opening the file picker cannot interrupt their replacements.

Eight final MacroActions are available: `Solucionar como resolvido`, `Solucionar como sem interação`, `Aguardar cliente até 3 dias úteis`, `Aguardar cliente até 1 semana`, `Aguardar produtor até 3 dias úteis`, `Aguardar produtor até 1 semana`, `Aguardar interno até 3 dias úteis`, and `Aguardar interno até 1 semana`. They run only in a focused HubSpot reply composer during that macro expansion or paste, and only when exactly one final label and no other configured label remains anywhere in that editor. If blocked, they stay pending; removing another label later does not trigger them automatically. Each removes its own line and one blank line below before opening **More send options**. The two solution actions choose **Send and set to Solucionado**, set pending information and validation to `Ok`, and select solution type `Resolvido` or `Sem interação`. The waiting actions choose **Send and set to Pendente**, select `Aguardando cliente`, `Aguardando produtor`, or `Aguardando tecnologia`, and set Data de retorno. Three business days skip Saturday and Sunday; one week means seven calendar days. The field's `MM/DD/YYYY` or `DD/MM/AAAA` format determines the text entered. The validation option has an internal `ok` value and a visible `Ok` label; compare the selected value or normalize display text. Scope option lookup to the dropdown opened by that field, with a unique visible open-option fallback. HubSpot's dependent panel can exist before its status badge or fields finish rendering, so wait for the expected badge and controls before entering values. TicketHelper focuses **Apply** and never clicks it. If preparation fails, it closes the dependent panel and restores the label when the editor remains unchanged. A red notice names the failed step and a console warning records its code; the pending label remains for manual handling or a later macro expansion.

Ticket-owned plain text inputs and textareas, including the transfer dialog's Descrição field, replace data labels from newly expanded or pasted macros. Their pending count follows the input cursor without per-character red highlighting, which native textareas do not support. Cc, receipt upload, and final actions require the reply composer and remain pending in these fields. They retain the active ticket and owner-epoch checks before replacing text.

TicketHelper's HubSpot-only macro autofill is configured in Options under **Autopreenchimento de Macros**, below Shortcuts and above Producer Notices. The user stores the label original spelling with an action choice in `chrome.storage.local` under `macroAutofillRules`. An empty label deletes its row; an unassigned label remains pending when used in a macro. Matching ignores letter case while preserving exact characters and spaces otherwise. Duplicate labels that differ only by letter case are rejected in Options and on import. Data actions are `Colar email de suporte` (selected Fatura), `Colar nome do produto` (selected Fatura), `Colar ID da fatura` (selected Fatura), `Colocar produtor em cópia` (selected Fatura), `Baixar comprovante do reembolso` (selected Fatura and HubSpot upload option), `Colar dados da fatura` (the selected invoice summary), `Colar nome do cliente` (first word of the active ticket name, capitalized), `Colar email do cliente` (active ticket email), `Colar emails censurados` (the completed Órbita masked-email list or the masked ticket email in a confirmed no-account case), and `Saudação por horário` (device local time: Bom dia 04:00–11:59, Boa tarde 12:00–18:59, Boa noite 19:00–03:59). The eight final actions are defined above. Further actions should be added to the shared action registry and resolved through focused handlers.

After a macro expansion or eligible paste, every configured label still present in that ticket's reply editor is counted, including labels without an assigned action. The persistent `N Pendentes` popup anchors at the focused typing caret, follows caret moves, and retains the last caret position when focus leaves the editor until all matches are removed. Its four corner placements keep it within the viewport. A light red CSS Custom Highlight marks the text without injecting nodes into HubSpot's ProseMirror document. An observer on only the tracked editor updates the count and marking after text edits; route changes, editor removal, or disabling TicketHelper clear the visual. Pending marks are advisory and do not submit a reply or change the saved macro.

Options rows use one shared divider at about 38% of the available width. Each label field is right-aligned against it and grows leftward; if needed, the divider moves right for every row together. The action field starts at the shared divider. The `+ Adicionar Etiqueta` button sits closer to the heading when the list is empty. Both it and `+ Adicionar Aviso` use a fixed one-fifth section width.

Options now offers Import and Export icons to the right of `+ Adicionar Etiqueta`. Export is disabled when there are no saved labels; clicking an enabled icon downloads immediately, with no persistent status row. The filename uses `TicketHelper-AutopreenchimentoDeMacros-ddmmyy.txt`, where the date is local. The UTF-8 text export starts with the exact first line `1 Autopreenchimento de Macros`, a blank line, then each label and displayed action name on two successive lines with a blank separator. An unassigned action has an empty value line and remains unassigned on import. Import accepts only this section header, known action names, and labels unique without regard to letter case; it validates the entire file before replacing `macroAutofillRules` in `chrome.storage.local`. A wrong-section or malformed file leaves saved rules unchanged. The icon row sits at the Add button's height; browser spellcheck is disabled in Options inputs.

ProKeys 4.0.2 inserts a completed rich-text macro as a new `.prokeys-snippet-text` element and fires an input event on that span. TicketHelper macros use `.th-macro-inserted`. `macro_autofill.js` captures these insertions before HubSpot normalizes the editor and observes newly added nodes. A normal paste into the focused HubSpot ticket editor also triggers MacroActions when the pasted text contains a configured label. It lets HubSpot paste first, then isolates only the newly inserted text using the editor's before/after text and the selection range; it does not scan old text or typing. If the inserted span changes, ticket ownership/focus changes, or the exact text no longer matches before an asynchronous value arrives, it leaves the label untouched. The existing rich macro path, including images, is unchanged.

ProKeys 4.0.2 has a user-driven JSON/CSV export/import path but no cross-extension message interface for TicketHelper to request or edit snippets directly. Its content script's `giveFreshData` message is internal. Chrome extension storage and context menus are scoped to each extension. ProKeys' published license restricts copying its code into another app or distributing a fork. The owner chose an original TicketHelper library with a one-time ProKeys JSON import; see `docs/MACRO_LIBRARY_MODEL.md`. Do not write to another extension's browser profile files.

The owner proposed a shortcut in a text editor that captures highlighted text, opens a small abbreviation prompt, and saves a new macro for immediate use. ProKeys 4.0.2 creates snippets in its own Options editor and exposes no selected-text creation request to another extension; its right-click menu inserts existing snippets only. TicketHelper can open ProKeys' Options route and prepare text for a manual handoff, but cannot prefill or submit that extension's form through supported extension APIs. A truly one-step save and live catalog requires TicketHelper to own an original macro store and expansion flow, or an owner-provided ProKeys integration API. Confirm whether the macro must physically live in ProKeys before implementing the creation UI, and preserve selected rich text versus plain text according to the owner's choice.

Earlier assisted-creation ideas targeted ProKeys' own import dialog and required manual Restore; that is not the chosen direction. The owner has now chosen the original TicketHelper macro library described in `docs/MACRO_LIBRARY_MODEL.md`. Creating a new macro from selected page text remains a later feature, after the base library is live-tested.

Before any replacement, the content script requires the focused HubSpot editor, ticket route, visible ticket header, locally active ticket, and popup owner tab/epoch to agree. It repeats those synchronous checks immediately before changing the text, so a route or focus switch while a value is pending leaves the label untouched. The owner epoch is sent with each ticket-data request; A-B-A switching cannot reuse an answer from A's earlier ownership. A greeting uses the same focused-editor gate even though its value comes from local time. The checks use the already available page and owner state and add no polling or extra network request.

`Colar emails censurados` uses the same value-selection helper as `Copiar Emails Censurados`, without touching the clipboard or requiring a selected Fatura. It needs the assigned BO2 customer tab and a completed, current-ticket Órbita result; a confirmed no-account or `Email sem conta` state masks the ticket email instead. Missing or pending results leave the label unchanged. The sender tab, ticket ID, and ownership epoch are checked before and after resolution.

The first resolver asks the background for the current ticket's selected Fatura support email using the existing `GET_SELECTED_FATURA_SUPPORT_EMAIL` result guard. It does not copy to the clipboard, focus a BO tab, or start a BO search. The background checks the sender tab, ticket ID, ownership epoch, selected invoice ID and product-row index, BO tab origin, and still-current selection before returning a lowercase email. The BO content script requires the exact visibly selected row, matching invoice ID and buyer signature; a different product within the same invoice cannot supply the value. An explicitly pinned invoice remains valid for its owning ticket even if it is outside the ticket's normal account search results. An unavailable or uncertain value leaves the label unchanged. The content script also rechecks snippet text and active rule revision before replacing case-insensitive occurrences inside that newly inserted snippet and dispatches one input event for the editor.

When a label starts immediately after a `<br>` or another element boundary, the replacement range must start in the label's own text node; its end must stay in that same node when the label ends at a boundary. Otherwise deleting the range can remove the surrounding line break and join separate macro lines. Keep the original macro structure and formatting around each label.

`Colar dados da fatura` uses the same five-field summary as the selected invoice copy command. It captures BackOffice's native invoice data without writing raw customer details to the clipboard, checks the selected invoice and product row, and returns only Fatura, Valor, Valor pago, Conteúdo, and Data da compra. For an Order Bump, Conteúdo lists the selected product first, followed by other contiguous same-ID products in visible top-to-bottom order, with commas and line breaks between names. Full product names come from their accessible labels when the visible text is truncated. Missing fields, changed selection, or changed product rows leave the macro label unchanged. The rich-text replacement inserts `<br>` elements for newline characters, including the blank lines between fields.

The owner observed support-email replacement working in an actual ProKeys expansion. The first implementation joined a separate tag line to the preceding line; boundary-aware replacement now preserves the line break. Continue live checks for the other actions, surrounding rich formatting and caret, isolation of newly pasted text, and stale-invoice refusal after ticket switching. Automated tests cover label matching, line-break boundaries, and ownership guards but cannot certify every third-party editor behavior.
