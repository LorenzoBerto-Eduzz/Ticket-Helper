# Macro Autofill Model

`Colocar produtor em cópia` uses the selected invoice support email. When that value resolves for the current ticket, TicketHelper removes the macro label before attempting the Cc operation; a failure to reach the Cc field does not restore the label. If HubSpot shows compact recipients, it opens that header first, then opens Cc in the focused ticket composer and enters the email. It counts existing Cc recipient tags before pressing Enter, then observes for a new tag. TicketHelper focuses the reply editor as soon as the count increases, or after 200 ms if it does not. It does not inspect the tag's displayed name or email. A standalone label removes its paragraph and one empty paragraph below, its following `<br>` and one extra `<br>` below, or the corresponding two newline characters; an inline label removes only itself. The blank line above remains. Missing invoice selection or changed ticket ownership before macro replacement leaves the label intact. `Colar nome do produto` inserts only the selected product name, formatted like the copy action.

`Colar ID da fatura` inserts the numeric invoice ID selected for the focused ticket; it does not require the BO popup to be open. `Colar nome do cliente` uses the part before `@` when the ticket name itself is an email, capitalizing only its first letter (for example `user.name@example.invalid` becomes `User.name`). The name copy shortcut and popup row use the same rule. `Colar email do cliente` inserts the active ticket's email in lowercase; it needs no selected invoice and leaves the label intact when the email is missing or the ticket ownership changes.

TicketHelper's HubSpot-only macro autofill is configured in Options under **Autopreenchimento de Macros**, below Shortcuts and above Producer Notices. The user stores exact, case-sensitive label text with an action choice in `chrome.storage.local` under `macroAutofillRules`. An empty label deletes its row; an unassigned action leaves a saved label inert. Duplicate labels are rejected in Options. Available actions are `Colar email de suporte` (selected Fatura), `Colar nome do produto` (selected Fatura), `Colar ID da fatura` (selected Fatura), `Colocar produtor em cópia` (selected Fatura), `Colar dados da fatura` (the selected invoice summary), `Colar nome do cliente` (first word of the active ticket name, capitalized), `Colar email do cliente` (active ticket email), and `Saudação por horário` (device local time: Bom dia 04:00–11:59, Boa tarde 12:00–18:59, Boa noite 19:00–03:59). Further actions should be added to the shared action registry and resolved through focused handlers.

Options rows use one shared divider at about 38% of the available width. Each label field is right-aligned against it and grows leftward; if needed, the divider moves right for every row together. The action field starts at the shared divider. The `+ Adicionar Etiqueta` button sits closer to the heading when the list is empty. Both it and `+ Adicionar Aviso` use a fixed one-fifth section width.

Options now offers Import and Export icons to the right of `+ Adicionar Etiqueta`. Export is disabled when there are no saved labels; clicking an enabled icon downloads immediately, with no persistent status row. The filename uses `TicketHelper-AutopreenchimentoDeMacros-ddmmyy.txt`, where the date is local. The UTF-8 text export starts with the exact first line `1 Autopreenchimento de Macros`, a blank line, then each label and displayed action name on two successive lines with a blank separator. An unassigned action has an empty value line and remains unassigned on import. Import accepts only this section header, known action names, and unique exact labels; it validates the entire file before replacing `macroAutofillRules` in `chrome.storage.local`. A wrong-section or malformed file leaves saved rules unchanged. The icon row sits at the Add button's height; browser spellcheck is disabled in Options inputs.

ProKeys 4.0.2 inserts a completed rich-text macro as a new `.prokeys-snippet-text` element and fires an input event on that span. TicketHelper macros use `.th-macro-inserted`. `macro_autofill.js` captures these insertions before HubSpot normalizes the editor and observes newly added nodes. A normal paste into the focused HubSpot ticket editor also triggers MacroActions when the pasted text contains a configured label. It lets HubSpot paste first, then isolates only the newly inserted text using the editor's before/after text and the selection range; it does not scan old text or typing. If the inserted span changes, ticket ownership/focus changes, or the exact text no longer matches before an asynchronous value arrives, it leaves the label untouched. The existing rich macro path, including images, is unchanged.

ProKeys 4.0.2 has a user-driven JSON/CSV export/import path but no cross-extension message interface for TicketHelper to request or edit snippets directly. Its content script's `giveFreshData` message is internal. Chrome extension storage and context menus are scoped to each extension. ProKeys' published license restricts copying its code into another app or distributing a fork. The owner chose an original TicketHelper library with a one-time ProKeys JSON import; see `docs/MACRO_LIBRARY_MODEL.md`. Do not write to another extension's browser profile files.

The owner proposed a shortcut in a text editor that captures highlighted text, opens a small abbreviation prompt, and saves a new macro for immediate use. ProKeys 4.0.2 creates snippets in its own Options editor and exposes no selected-text creation request to another extension; its right-click menu inserts existing snippets only. TicketHelper can open ProKeys' Options route and prepare text for a manual handoff, but cannot prefill or submit that extension's form through supported extension APIs. A truly one-step save and live catalog requires TicketHelper to own an original macro store and expansion flow, or an owner-provided ProKeys integration API. Confirm whether the macro must physically live in ProKeys before implementing the creation UI, and preserve selected rich text versus plain text according to the owner's choice.

Earlier assisted-creation ideas targeted ProKeys' own import dialog and required manual Restore; that is not the chosen direction. The owner has now chosen the original TicketHelper macro library described in `docs/MACRO_LIBRARY_MODEL.md`. Creating a new macro from selected page text remains a later feature, after the base library is live-tested.

Before any replacement, the content script requires the focused HubSpot editor, ticket route, visible ticket header, locally active ticket, and popup owner tab/epoch to agree. It repeats those synchronous checks immediately before changing the text, so a route or focus switch while a value is pending leaves the label untouched. The owner epoch is sent with each ticket-data request; A-B-A switching cannot reuse an answer from A's earlier ownership. A greeting uses the same focused-editor gate even though its value comes from local time. The checks use the already available page and owner state and add no polling or extra network request.

The first resolver asks the background for the current ticket's selected Fatura support email using the existing `GET_SELECTED_FATURA_SUPPORT_EMAIL` result guard. It does not copy to the clipboard, focus a BO tab, or start a BO search. The background checks the sender tab, ticket ID, ownership epoch, selected invoice ID and product-row index, BO tab origin, and still-current selection before returning a lowercase email. The BO content script requires the exact visibly selected row, matching invoice ID and buyer signature; a different product within the same invoice cannot supply the value. An explicitly pinned invoice remains valid for its owning ticket even if it is outside the ticket's normal account search results. An unavailable or uncertain value leaves the label unchanged. The content script also rechecks snippet text and active rule revision before replacing exact occurrences inside that newly inserted snippet and dispatches one input event for the editor.

When a label starts immediately after a `<br>` or another element boundary, the replacement range must start in the label's own text node; its end must stay in that same node when the label ends at a boundary. Otherwise deleting the range can remove the surrounding line break and join separate macro lines. Keep the original macro structure and formatting around each label.

`Colar dados da fatura` uses the same five-field summary as the selected invoice copy command. It captures BackOffice's native invoice data without writing raw customer details to the clipboard, checks the selected invoice and product row, and returns only Fatura, Valor, Valor pago, Conteúdo, and Data da compra. For an Order Bump, Conteúdo lists the selected product first, followed by other contiguous same-ID products in visible top-to-bottom order, with commas and line breaks between names. Full product names come from their accessible labels when the visible text is truncated. Missing fields, changed selection, or changed product rows leave the macro label unchanged. The rich-text replacement inserts `<br>` elements for newline characters, including the blank lines between fields.

The owner observed support-email replacement working in an actual ProKeys expansion. The first implementation joined a separate tag line to the preceding line; boundary-aware replacement now preserves the line break. Continue live checks for the other actions, surrounding rich formatting and caret, isolation of newly pasted text, and stale-invoice refusal after ticket switching. Automated tests cover label matching, line-break boundaries, and ownership guards but cannot certify every third-party editor behavior.
